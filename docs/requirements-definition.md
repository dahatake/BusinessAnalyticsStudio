## 1. 概要

### 1.1 事業背景

Business Analytics Studio は、ビジネス議論のための分析ボード（分析画面、AI、プレゼン、ワークスペース等）を提供する既存のブラウザーアプリである（出典: SRC-012 src/）。現状は、ビジネスシナリオ・KPI 測定・ユースケース作成の場面で、利用者が組織や業務を体系的な手法に沿って分析し、その結果を見比べる仕組みと、いま改善プロセスのどこにいるかを示す仕組みがない。また特定の企業について複数の Project を並行して扱う単位がない。MBA 分野で一般に知られる組織・プロセス分析の枠組み（Harvard Business Review などで解説される名称の参照のみ。SRC-010）を使えるようにし、議論の質と再現性を高める。

### 1.2 目的

| ID | 目的 | 成功指標 | 測定方法 |
|---|---|---|---|
| G-005 | 利用者が、一般的な組織・業務分析の手法に沿って業務や組織を分析し、パラメーターを編集しながら結果を確認できる | 手法を選んで結果を確認するまでを、案内なしで完了できた利用者の割合（目標値は未定。Q 不要のため PARAM 化せず、導入後に決める） | 利用者テスト（manual） |
| G-006 | 利用者が、業務改善プロセスの現在のステップを常に把握できる | ステッパーで現在のステップを正しく答えられた割合（目標値は未定） | 利用者テスト（manual） |
| G-007 | 特定の企業について複数の Project を取り違えなく管理できる | Project 間のデータ混在の発生件数 0 | System Test（AC-209） |

### 1.3 事業妥当性の判定

条件付き。根拠: 依頼原文と既存アプリの目的との整合は確認したが、利用者数・効果の数値は入力にない。条件: Project データの保存先と共有範囲（Q-009）、AI 利用時の外部送信（Q-011）の決定。

## 2. 対象と対象外

対象: 既存アプリへの次の追加。(1) 組織・業務の分析手法の選択、ビュアー切替、パラメーター編集、結果確認。(2) 改善プロセスのステッパー。(3) 企業と、その下の複数 Project の管理。
対象外: 既存の分析ボード・AI・プレゼン・エクスポート等の既存機能の要求の起こし直し（AUD-001）。HBR 等の本文の複製・転載（手法の名称と一般的な枠組みの参照のみ）。外部システムとの連携（Q-010 の決定まで）。

## 3. 前提・制約

### 3.1 既定制約（要求定義プロンプトの常設方針）

- ui_policy-1 利用者がレイアウトを変更できるモダンな UI（決定状態: 承認済み・既定制約）
- ui_policy-2 ペルソナごとの既定の情報表現（決定状態: 承認済み・既定制約）

### 3.2 パラメータ（PARAM）

閾値・期間・件数などの値は、要求と受入基準に直接書かず、ここで定義して `{PARAM-xxx}` の形で参照します。

| ID | 名前 | 値 | 単位 | 根拠 | 決定状態 |
|---|---|---|---|---|---|
| PARAM-030 | 業務改善ステップ数 | 5 | 個 | AI提案（課題定義→現状分析→KPI 測定→ユースケース作成→施策計画）。ステップ名と数は PARAM と状態表で変更できる | 承認済み（包括承認 2026-10-12・approval_policy） |
| PARAM-031 | 企業ごとの Project 数の上限 | 50 | 件 | AI提案。一覧の操作性の仮の上限。変更で戻せる | 承認済み（包括承認 2026-10-12・approval_policy） |
| PARAM-032 | パラメーター変更から結果反映までの上限時間 | 2 | 秒 | AI提案。通常規模のデータ（既存サンプル相当）での目安 | 承認済み（包括承認 2026-10-12・approval_policy） |

### 3.3 用語

| 用語 | 定義 | 禁止同義語 |
|---|---|---|
| 企業 | Project をまとめる単位。利用者が分析対象として登録する特定の会社・組織 | 顧客先 |
| Project | 企業の下で、業務改善の取り組み 1 件を表す単位。分析とステッパーの位置を持つ | 案件 |
| 分析 | 分析手法とパラメーターを選び、結果を得る 1 回の取り組み | なし |
| 分析手法 | SWOT 分析、ファイブフォース分析、バリューチェーン分析、3C 分析、バランスト・スコアカードなどの一般的な枠組み | なし |
| ビュアー | 分析結果を表示する見せ方（表、マトリクス、図、グラフ） | なし |
| 業務改善ステップ | 業務改善プロセスの段階。ステッパーで表示する | なし |

### 3.4 状態

| 対象エンティティ | 状態 | 遷移の条件 |
|---|---|---|
| Project | 進行中→アーカイブ | 利用者がアーカイブ。戻せる |
| 分析 | 編集中→結果確認済み | 利用者が結果を確認（結果を表示）したとき |
| 業務改善ステップ | 未着手→進行中→完了 | 利用者がそのステップの作業を開始・完了したとき |

## 4. ペルソナ

| ペルソナ | 業務 | 主要な判断 | 使うデータ | 判断の頻度と緊急度 | 役割 | 出典 |
|---|---|---|---|---|---|---|
| 事業企画担当 | 事業シナリオ・KPI・ユースケースの作成 | どの課題を優先するか | 分析入力値、KPI、数量 | 週次・中 | アプリ内の編集者（権限の正本は Q-009 で決定） | SRC-010（調査したが該当なし。仮説） |
| 業務改善リーダー | 複数 Project の進行管理 | 各 Project の現在ステップと遅れ | ステップ状態、日程 | 日次・中 | 同上 | SRC-010（仮説） |
| 経営層・意思決定者 | 分析結果を見て方針を決める | 施策の採否 | 分析結果の要約 | 月次・高 | 閲覧者 | SRC-010（仮説） |

## 5. 利用シナリオ

主要: 利用者は企業と Project を選び、ステッパーで現在のステップを確認し、分析手法を選んでパラメーターを編集し、ビュアーで結果を確認する。代替: KPI 測定・ユースケース作成の画面から分析を起動する（FR-133）。中断と再開: Project を閉じて再度開くと、ステップの位置と分析の入力値が残る（AC-207、Q-009）。変更と取消: パラメーターを既定値に戻す（AC-199）、Project をアーカイブする（AC-208）。失敗と復旧: 不正な入力値はエラー表示のうえ入力を失わない（AC-198）。

### 6.1 機能要求

#### FR-133 分析手法の選択と開始
- 要求: 利用者は、ビジネスシナリオ・KPI 測定・ユースケース作成の各作業から、組織・業務の分析手法（SWOT 分析、ファイブフォース分析、バリューチェーン分析、3C 分析、バランスト・スコアカード）を選んで分析を開始できる。
- 決定状態: 承認済み（依頼 2026-10-12）　出自: 依頼原文　優先度: MUST（依頼の中核）
- 上位: G-005　出典: 依頼原文、SRC-010（手法の名称のみ。具体的な 5 手法の選定は AI提案として包括承認）
- 対象エンティティ: 分析　関係する状態: 編集中　参照パラメータ: なし
- 関連する既存資産: なし
- 受入基準 AC-195: Project を開いている利用者が分析手法の一覧から 1 つを選ぶと、その手法の入力欄を持つ分析が開始され、一覧に上記 5 手法が含まれる。
  - 検証レベル: system
- 受入基準 AC-196: ビジネスシナリオ・KPI 測定・ユースケース作成の 3 つの作業の各画面から、分析の開始操作で同じ手法の一覧に到達でき、元の作業に戻れる。
  - 検証レベル: integration

#### FR-134 パラメーターの編集と結果の更新
- 要求: 利用者は、分析のパラメーター（手法ごとの項目の値・重み・分類）を編集でき、編集した結果が分析結果に反映される。
- 決定状態: 承認済み（依頼 2026-10-12）　出自: 依頼原文　優先度: MUST（依頼の中核）
- 上位: G-005　出典: 依頼原文
- 対象エンティティ: 分析　関係する状態: 編集中　参照パラメータ: PARAM-032
- 関連する既存資産: なし
- 受入基準 AC-197: 分析のパラメーターを変更した利用者が、変更から {PARAM-032} 以内に、表示中の結果に変更が反映されたことを確認できる。
  - 検証レベル: system
- 受入基準 AC-198: 範囲外・型違いの値を入力すると、原因と直し方を示すエラーが表示され、ほかの入力済みの値は失われず、結果は直前の有効な状態のままである。
  - 検証レベル: integration
- 受入基準 AC-199: 利用者がパラメーターを既定値に戻す操作を行うと、全パラメーターが手法の既定値になる。
  - 検証レベル: unit

#### FR-135 ビュアーの切替と結果の確認
- 要求: 利用者は、分析結果を複数のビュアー（表、マトリクス、図、グラフのうち手法で成り立つもの）で切り替えて確認できる。
- 決定状態: 承認済み（依頼 2026-10-12）　出自: 依頼原文　優先度: MUST（依頼の中核）
- 上位: G-005　出典: 依頼原文
- 対象エンティティ: 分析　関係する状態: 編集中→結果確認済み　参照パラメータ: なし
- 関連する既存資産: なし
- 受入基準 AC-200: 結果を表示している利用者がビュアーを切り替えたとき、選択中の項目・絞り込みが保たれ、同じ結果の値が表示される。
  - 検証レベル: system
- 受入基準 AC-201: 結果の画面に、採用した手法名とパラメーターの値が表示され、結果を表示した分析は「結果確認済み」になる。
  - 検証レベル: integration

#### FR-136 業務改善ステッパー
- 要求: 利用者は、画面の上部に、業務改善プロセスの全ステップ（{PARAM-030} 個）と現在のステップを常に確認できる。
- 決定状態: 承認済み（依頼 2026-10-12）　出自: 依頼原文　優先度: MUST（依頼の中核）
- 上位: G-006　出典: 依頼原文、SRC-010（ステップ名は AI提案として包括承認）
- 対象エンティティ: 業務改善ステップ　関係する状態: 未着手→進行中→完了　参照パラメータ: PARAM-030
- 関連する既存資産: なし
- 受入基準 AC-202: Project を開いている利用者に、画面上部で {PARAM-030} 個のステップが順に並び、現在のステップが他と区別でき、完了済みと未着手が識別できる。
  - 検証レベル: system
- 受入基準 AC-203: 利用者が別の画面（分析・KPI 測定・ユースケース作成など）へ移動しても、ステッパーが表示され続け、その画面に対応するステップが現在の位置になる。
  - 検証レベル: system
- 受入基準 AC-204: 利用者がステッパーのステップを選ぶと、そのステップの作業画面に移動できる。
  - 検証レベル: integration

#### FR-137 企業の登録と複数 Project の管理
- 要求: 利用者は、特定の企業を登録し、その企業の下に複数の Project を作成・一覧・名称変更・アーカイブできる。
- 決定状態: 承認済み（依頼 2026-10-12）　出自: 依頼原文　優先度: MUST（依頼の中核）
- 上位: G-007　出典: 依頼原文
- 対象エンティティ: 企業、Project　関係する状態: 進行中→アーカイブ　参照パラメータ: PARAM-031
- 関連する既存資産: なし
- 受入基準 AC-205: 利用者が企業を登録し、その企業に 2 つ以上の Project を作成すると、企業ごとの Project 一覧に表示される。
  - 検証レベル: system
- 受入基準 AC-206: 1 企業の Project が {PARAM-031} 件に達しているとき、新規作成が拒否され、理由が示され、既存の Project は変わらない。
  - 検証レベル: integration
- 受入基準 AC-207: アプリを閉じて再び開いた利用者が、企業・Project・ステッパーの位置・分析の入力値を復元できる。保存先と保存範囲は未決定。
  - 検証レベル: system
  - BLOCKED: Q-009（保存先・保存範囲が未決定）
- 受入基準 AC-208: 利用者が Project をアーカイブすると進行中の一覧から外れ、アーカイブ一覧から復元できる。名称変更が一覧に反映される。
  - 検証レベル: integration

#### FR-138 Project の切替とデータの分離
- 要求: 利用者は、Project を切り替えたときに、ほかの Project や企業の分析・ステップ・メモが混ざらずに表示される。
- 決定状態: AI提案／承認待ち　出自: AI提案　優先度: MUST（取り違えは利用者データの誤りになるため。利用者データに触れるため承認依頼とする）
- 上位: G-007　出典: 依頼原文（複数 Project 管理の前提）
- 対象エンティティ: Project　関係する状態: 進行中　参照パラメータ: なし
- 関連する既存資産: なし
- 受入基準 AC-209: Project A と Project B にそれぞれ異なる分析を作成した利用者が切り替えたとき、各 Project に自分の分析とステッパーの位置だけが表示される。
  - 検証レベル: system
- 受入基準 AC-210: Project を切り替えても、切替前の Project の未保存の入力値が失われず、確認の案内が出る。
  - 検証レベル: integration

#### FR-139 企業・Project の識別子と正本
- 要求: 利用者は、企業と Project を、他システムの識別子と対応付けられる。
- 決定状態: AI提案／承認待ち　出自: AI提案　優先度: MAY（連携先が未確認のため）
- 上位: G-007　出典: Q-010
- 対象エンティティ: 企業、Project　関係する状態: 進行中　参照パラメータ: なし
- 関連する既存資産: なし
- 受入基準 AC-211: 企業と Project に識別子が付与され、重複しない。外部の識別子との対応は Q-010 の回答後に定める。
  - 検証レベル: integration
  - BLOCKED: Q-010（正本システムと識別子の体系が未決定）

#### FR-140 分析結果の AI 下書き
- 要求: 利用者は、分析の入力項目について AI による下書きを依頼し、採否を決めて反映できる。
- 決定状態: AI提案／承認待ち　出自: AI提案　優先度: MAY（価値は仮説。外部送信を伴うため承認依頼）

- 関連する既存資産: なし

  - 検証レベル: integration
  - BLOCKED: Q-011（外部送信の可否が未決定）

### 6.2 非機能要求

#### NFR-UX-006 分析画面のレイアウト変更
- 要求: 利用者は、分析画面の構成要素（手法の入力、ビュアー、結果の要約）の位置・大きさ・表示を変更し、既定に戻せる。
- 決定状態: AI提案／承認待ち　出自: AI提案　優先度: SHOULD（常設方針 ui_policy-1 の具体化）
- 上位: G-005　出典: 3.1 ui_policy-1、SRC-011
- 対象エンティティ: 分析　関係する状態: 編集中　参照パラメータ: なし
- 関連する既存資産: 共通部品「ワークスペース」、共通部品「コマンドパレット」
- 受入基準 AC-214: 分析画面でレイアウトを変更した利用者が、既定に戻す操作で既定に戻せ、変更中に入力値・選択・絞り込みが失われない。保存の単位と保存先は未決定。
  - 検証レベル: system
  - BLOCKED: Q-009（保存の単位と保存先）
- 受入基準 AC-215: 移動と大きさの変更が、ドラッグなしの手段（メニューまたはキーボード、コマンドパレット）でも行える。
  - 検証レベル: integration
