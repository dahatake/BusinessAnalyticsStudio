# 要求: A. 共通アプリ本体（雛形）— データカタログ（エンティティとユースケースの対応・企業データカタログとの突合）

索引・前提・PARAM・用語・質問票は [要求定義書](../requirements-definition.md) にあります。
「標準の検証条件」は、要求定義書 §3.5 のとおりです。依頼: run 202610142019（SRC-016）。

## 12. データカタログ

Project を開いている利用者が、業務改善で扱うデータエンティティを一覧し、どのユースケースがどのエンティティを使うかを対応表で確かめ、企業がすでに持つデータカタログと突き合わせて、未掲載のものを ToDo にできるようにする。導出と突合は端末内で完結し、AI には接続しない（NFR-SEC-004、C-07 のモック条件）。

#### FR-159 データカタログの画面（エンティティの一覧と詳細）
- 要求: Project を開いている利用者は、新しい画面「データカタログ」で、その Project のデータエンティティの一覧と、選んだデータエンティティの詳細（名称、説明、導出元の課題・解決策・フロー、関連するユースケース）を確認できる。データエンティティは、顧客パックの課題・解決策・フロー（FR-001〜FR-005、FR-021）が参照するエンティティと、ユースケース（FR-158）の導出元（`src/usecase/model.ts` の `source`）から導出し、保存しない。ユースケースは、FR-158 で登録済みのものだけを導出の元とし、導出の候補（未登録）は元にしない（候補は保存されないので、登録のたびに一覧が変わることを防ぐ。登録済みのユースケースの追加・編集・削除に伴う一覧の変化は、次に開いた画面に反映される）。名称の表記ゆれ（全角・半角、大文字・小文字、前後の空白）は正規化して同じ名称を 1 件にまとめる。導出の元（課題・解決策・フロー）がない、または顧客パックがないときは、0 件とし、その理由を表示する。
- 決定状態: 承認済み（依頼 2026-10-14）　出自: 依頼原文　優先度: MUST（対応表・突合・ToDo 追加のすべての入力になるため）
- 上位: G-005　出典: 依頼原文、SRC-016、FR-158、FR-001〜FR-005、FR-021
- 対象エンティティ: データエンティティ、Project、顧客パック、課題、解決策　関係する状態: なし　参照パラメータ: なし
- 関連する既存資産: 共通部品「画面の登録」（画面を足すときの登録）、共通部品「ユースケース・アニメーション」（FR-158 の `source`。変えない）、共通部品「企業・Project の端末内保存」

  - 検証レベル: system
- 受入基準 AC-295: 課題・解決策・フローが「受注」「受注 」「ＪＵＣＨＵ」の表記違いで同じエンティティを参照する入力を導出したとき、表記ゆれを正規化した名称で 1 件にまとまり、導出元はすべて詳細に列挙される。
  - 検証レベル: unit
- 受入基準 AC-296: 顧客パックがない Project、または課題・解決策・フローのどれも参照するエンティティを持たない顧客パックを開いたとき、一覧は 0 件で、理由が表示され、画面は壊れず、他の画面の操作を妨げない。
  - 検証レベル: integration

#### FR-160  エンティティ×ユースケースの対応表と明示の紐づけ
- 要求: Project を開いている利用者は、データカタログの画面で、データエンティティ（行）×ユースケース（列）の対応表を確認できる。対応は、課題・解決策・フローと、ユースケースの導出元（`src/usecase/model.ts` の `source`）から導出した「導出」と、利用者が明示した「明示」に分けて表示する。利用者は、明示の紐づけを追加・削除できる。導出の紐づけは、元の課題・解決策・フローを変えない限り削除できない。明示の紐づけは、その Project の端末内に保存し、Project ごとに分離する（FR-138、NFR-SEC-004）。存在しないデータエンティティやユースケースへの紐づけ、すでにある同じ組の追加は拒否し、既存の紐づけを変えない。対応表の列と紐づけの対象は、FR-158 で登録済みのユースケースだけとする（導出の候補は含めない）。登録済みのユースケースを削除したときは、そのユースケースへの明示の紐づけも同時に削除する（連動削除。紐づけは削除したユースケースの ID を持つため、残すと存在しない対象への紐づけになる）。削除したユースケースを同じ内容で再登録しても、削除した紐づけは復活しない。
- 決定状態: 承認済み（依頼 2026-10-14）　出自: 依頼原文　優先度: MUST（依頼原文。ToDo に関連ユースケースを載せる（FR-162）元になるため）
- 上位: G-005　出典: 依頼原文、SRC-016、FR-158、FR-138
- 対象エンティティ: データエンティティ、ユースケース、ユースケースの紐づけ、Project　関係する状態: 種別（導出／明示）　参照パラメータ: なし
- 関連する既存資産: 共通部品「企業・Project の端末内保存」（保存の追加項目。保存の形は変えずに足す）、共通部品「ユースケース・アニメーション」（ユースケースの一覧。変えない）
- 受入基準 AC-297: 標準の検証条件で、お手本パックの Project を開き、ユースケースを登録した利用者が対応表を開くと、導出の対応が「導出」と、明示の対応が「明示」とセルに文字で区別して表示される（色だけに依存しない）。ユースケースが 0 件のときは、列が空で、その理由が表示される。
  - 検証レベル: system
- 受入基準 AC-298: 利用者が空のセルに明示の紐づけを追加すると、セルが「明示」になり、アプリを閉じて開き直しても残り、別の Project の対応表には現れない。その明示の紐づけを削除するとセルが空に戻る。「導出」のセルには削除の操作がなく、削除を試みても対応は変わらない。
  - 検証レベル: integration
- 受入基準 AC-299: 存在しないエンティティ名またはユースケースの ID を指定した紐づけの追加は拒否され、原因が表示される。すでにある同じ（エンティティ、ユースケース）の組を追加しても件数は増えず、既存の紐づけは変わらない。
  - 検証レベル: unit
- 受入基準 AC-313: 明示の紐づけを持つユースケースを削除すると、その紐づけも削除され、対応表のセルは空に戻り、アプリを閉じて開き直しても残らない。他のユースケースの紐づけは変わらない。削除したユースケースを同じ名称で再登録しても、その紐づけは復活しない。
  - 検証レベル: integration
#### FR-161 企業データカタログの取り込みと突合
- 要求: Project を開いている利用者は、企業がすでに持つデータカタログを、JSON または CSV のファイルとして取り込み、データカタログの画面で、BAS のデータエンティティとの突合の結果を「一致」「差異」「BASのみ」「カタログのみ」の 4 区分で確認できる。取り込みは利用者のブラウザーの中だけで完結し、ファイルの内容を端末外に送信しない（NFR-SEC-004）。企業データカタログが Web サイトにある場合、利用者は URL を出典として記録できるが、アプリは URL にアクセスせず、内容を取得しない。突合は、名称（表記ゆれを正規化したもの）と ID で行う。ファイルの大きさは {PARAM-050} まで、項目数は {PARAM-051} 件までとする。形式が不正、必須の項目（名称）がない、上限を超えるファイルは拒否し、原因を表示して、すでに取り込んでいる企業データカタログと突合の結果を変えない。
- 決定状態: 承認済み（依頼 2026-10-14）　出自: 依頼原文　優先度: MUST（依頼原文。企業のデータ連携では、連携先の体系を確認せずに独自のデータ定義を持つと後の名寄せが大きな手戻りになるため）。取り込みの項目の形・上限値・再取り込みの扱いは AI提案を包括承認（包括承認 2026-10-14・approval_policy。端末内の表示だけで、PARAM と規則の変更で戻せる。A-41）
- 上位: G-005　出典: 依頼原文、SRC-016、Q-018（突合の鍵・対応表の保守者）、NFR-SEC-004、A-41
- 対象エンティティ: 企業データカタログ、データエンティティ、突合結果、Project　関係する状態: 取り込み状態（未取り込み→取り込み済み）、区分（一致／差異／BASのみ／カタログのみ）　参照パラメータ: PARAM-050、PARAM-051
- 関連する既存資産: 共通部品「企業・Project の端末内保存」（取り込んだ内容と出典の URL を Project ごとに保存。NFR-SEC-004）、FR-132（外部送信の既定は変えない）
- 受入基準 AC-300: 標準の検証条件で、利用者が有効な企業データカタログの JSON を取り込むと、データエンティティごとに「一致」「差異」「BASのみ」、カタログにだけある項目が「カタログのみ」として、4 区分の件数と一覧が表示される。区分は文字で表示される。
  - 検証レベル: system
- 受入基準 AC-301: 名称と説明の列を持つ CSV（先頭行が見出し。引用符つきの項目を含む）を取り込むと、JSON と同じ内容の企業データカタログとして扱われ、同じ突合の結果になる。
  - 検証レベル: unit
- 受入基準 AC-302: 突合の規則（判定は次の順に行い、最初に当てはまる区分にする。1 つの組は必ず 1 区分だけになる）。①対応づけ: BAS のデータエンティティとカタログの項目は、名称が表記ゆれの正規化後に一致する、または、カタログの項目の BAS の ID を示す任意の欄（`basId`）がそのエンティティの ID と一致するときに対応づく。②対応づく組のうち、説明が同じで、かつ ID が両方にあるときは ID も同じなら「一致」、それ以外（説明が異なる、または ID が両方にあって異なる。名称・説明が同じで ID だけが異なる組を含む）は「差異」。③対応づくカタログの項目がない BAS のデータエンティティは「BASのみ」、対応づく BAS のデータエンティティがないカタログの項目は「カタログのみ」。ID がどちらか一方にしかないことは、差異の理由にしない。
  - 検証レベル: unit
- 受入基準 AC-314: 名称と説明が同じで ID だけが異なる組は「差異」になり「一致」にならない。名称と説明が同じで ID が片方にしかない組は「一致」になる。名称が異なり ID が一致する組で説明が同じなら「一致」、異なれば「差異」になる。どの組も、4 区分のうち 1 つにだけ数えられ、4 区分の件数の合計が組の総数と一致する。
  - 検証レベル: unit
- 受入基準 AC-303: 壊れた JSON、名称の欄がない CSV、{PARAM-050} を超えるファイル、{PARAM-051} 件を超える項目のファイルを取り込むと、それぞれ拒否されて原因と直し方が表示され、すでに取り込み済みの企業データカタログと突合の結果は取り込み前と同じままである。
  - 検証レベル: integration
- 受入基準 AC-304: 取り込みと突合の操作中に、アプリからのネットワーク要求が 0 件（ファイルの内容が端末外に送られない）で、URL を出典として入力して保存しても、その URL への要求が 0 件である。保存した URL は再起動後も出典として表示される。
  - 検証レベル: integration

#### FR-162 カタログ未掲載のエンティティの ToDo への一括追加
- 要求: Project を開いている利用者は、企業データカタログに載っていないデータエンティティ（突合の結果が「BASのみ」）を、自分の操作で、その Project の plan の tasks に ToDo として一括で追加できる。追加する ToDo の名称と説明に、対象のデータエンティティの名称と、関連するユースケース（FR-160 の導出と明示の両方）の名称を含める。同じ操作を繰り返しても、すでに追加したデータエンティティの ToDo は重複して作られない（冪等）。追加した ToDo は、他のデータ層（plan の tasks）と同じ場所（その Project の保存領域にある plan の tasks。顧客パックの `schema/plan.json` は読み取り専用で変更しない。Project の plan の tasks は、顧客パックの tasks に加えて Project 内の追加分を合わせたものとして扱い、表示は FR-022 の既存の表示に従う）に保存し、Project ごとに分離する（Q-017）。ToDo の識別子（冪等の鍵）は、データエンティティの正規化名（表記ゆれ正規化後の名称）から決まる固定の値（`data-catalog:<正規化名>`）とし、同じ鍵の ToDo がすでにあるときは追加しない（内容も変えない）。企業データカタログを取り込んでいないとき、または「BASのみ」が 0 件のときは追加できず、その理由を表示する。
- 決定状態: 承認済み（依頼 2026-10-14）　出自: 依頼原文　優先度: SHOULD（依頼原文。カタログ未掲載の確認作業を、取りこぼさず進行管理に載せるため）。保存先は Q-017 の回答で確定（承認済み（Q-017 2026-10-14））
- 上位: G-005　出典: 依頼原文、SRC-016、Q-017、FR-137、FR-138、NFR-SEC-004
- 対象エンティティ: ToDo、データエンティティ、突合結果、ユースケース、Project　関係する状態: 追加状態（未追加→追加済み）　参照パラメータ: なし
- 関連する既存資産: 共通部品「企業・Project の端末内保存」（plan の tasks と同じ Project 内の保存先。保存の形は変えずに足す）、FR-022（ガントチャートの工程。ToDo の表示は本要求の範囲外で、既存の表示に従う）
- 受入基準 AC-305: 標準の検証条件で、企業データカタログを取り込んで「BASのみ」が 2 件ある Project で、利用者が「未掲載を ToDo に追加」を実行すると、2 件の ToDo が plan の tasks に追加される。各 ToDo の名称と説明に、対象のデータエンティティの名称と関連するユースケースの名称が含まれ、追加の件数が表示される。
  - 検証レベル: system
- 受入基準 AC-306: 同じ操作をもう一度実行しても plan の tasks の件数は増えず、すでに追加したエンティティの ToDo の内容は変わらない。その後に「BASのみ」のエンティティが 1 件増えたときの実行では、増えた 1 件だけが追加される。
  - 検証レベル: unit
- 受入基準 AC-307: 追加した ToDo は、アプリを閉じて開き直しても残り、plan の tasks と同じ場所に、データエンティティの正規化名から決まる識別子（`data-catalog:<正規化名>`）で保存され、別の Project の ToDo には現れない。顧客パックの plan は変わらない。
  - 検証レベル: integration
- 受入基準 AC-308: 企業データカタログを取り込んでいない Project、または「BASのみ」が 0 件の Project で追加の操作を行うと、ToDo は追加されず、理由が表示される。
  - 検証レベル: integration
