# 要求: 外部連携カタログ（外部のアプリ・データとの連携の確認項目）

索引・前提・PARAM・用語・質問票は [要求定義書](../requirements-definition.md) にあります。「標準の検証条件」は、要求定義書 §3.5 のとおりです。依頼: run 202610160502（SRC-022）。

## 13. 外部連携カタログ

このアプリ（と、その開発・生成パイプライン）が、外部のアプリ・サービス・データと API・ファイル・DB・イベントなどでやり取りするとき、要求を決める段階で確かめておくべき項目を、`docs/integration-catalog.md`（外部連携カタログ）に 1 連携 1 行で記録して管理する。これは要求定義のレベルの確認項目で、設計書（具体的な実装の方式、API 定義、スキーマ、製品の選定）ではない。連携先ごとの「確かめたか・何が決まっていないか」を、後から来た人や AI エージェントが 1 か所で把握できるようにする。

扱う範囲は、アプリが外部の相手とやり取りする連携（要求定義書 §8 の連携先を含む）である。顧客の本番システムとの連携は、§2 の対象外のままで、この要求は対象外を広げない（追加する場合は、先に §2 を利用者が変更する）。

記入の規則（FR-188〜FR-197 に共通）: カタログの各欄は、(a) 具体的な値、(b)「なし（理由）」、(c)「TBD（Q-xxx）」のどれかで埋める。空欄、「適宜」「一般的に」「十分な」のように結果が読み手で変わる語だけの記述、Q-xxx のない TBD は「空」とみなす。「TBD（Q-xxx）」は、検査が警告として一覧し（失敗にはしない）、Q-xxx が回答済みになったら値に置き換える。以降の受入基準で「空」と書くのは、この意味である。値は閾値・期間・件数を含むとき PARAM で定義して `{PARAM-xxx}` で参照する。

#### FR-188 外部連携カタログの管理データ
- 要求: 要求定義の担当者と実装者は、外部連携を、管理データの 1 つである外部連携カタログ（`docs/integration-catalog.md`）で一元的に把握できる。カタログは、1 連携 1 行の表で、連携名（一意）、連携先、方向、種別、状態、関連する要求 ID、FR-189〜FR-197 の確認項目の欄、最終確認日を持つ。既存のカタログ（`docs/catalog.md`）と同じく、要求定義書とつながる ID と名前で書き、詳細はリンク先に任せる。「確認項目」は FR-189〜FR-197 の項目を指す（FR-188 の管理データの形と FR-198 の結線は確認項目ではなく、別の検査で確かめる）。カタログは確認項目を次の列にまとめる。空かどうかの判定は列（欄）単位で行い、1 つの列に複数の項目を書くときは、各項目に値・「なし（理由）」・「TBD（Q-xxx）」のどれかを書く（列の中の項目ごとの漏れは、検査ではなく更新時のレビューで確かめる）。
  - 正本・識別子 → FR-189（連携先・方向・種別・状態・連携名の列と合わせて）／認証・認可、資格情報の管理 → FR-190／送受信するデータ・個人情報・機密区分、送信の条件 → FR-191／頻度・量・SLA、タイムアウト → FR-192／失敗時・再試行・冪等性 → FR-193／バージョン・互換・変更の通知 → FR-194／監視・監査ログ → FR-195／規約・ライセンス・コスト → FR-196／テスト用スタブ・実接続の確認 → FR-197
- 決定状態: 承認済み（依頼 2026-10-16）　出自: 依頼原文　優先度: MUST（外部連携の確認項目の記録先がないと、以降の要求が検査できないため）
- 上位: G-004　出典: 依頼原文、SRC-022
- 対象エンティティ: 外部連携カタログ、外部連携　関係する状態: なし　参照パラメータ: なし
- 関連する既存資産: カタログ（`docs/catalog.md`）の作法（1 行 1 項目）、要求定義書 §8（外部連携とマスター・ID）
- 受入基準 AC-403: リポジトリに外部連携カタログがあり、読み手が連携名・連携先・方向・種別・状態・関連する要求 ID・FR-189〜FR-197 の確認項目・最終確認日の欄を、連携ごとに 1 行で確認できる。
  - 検証レベル: integration
- 受入基準 AC-404: 同じ連携名の行が 2 行ある、または連携名が空の行があるカタログに対し、検査は失敗し、該当の行を示す。

#### NFR-SEC-006 外部連携カタログに秘密情報と個人情報の実データを書かない
- 要求: 外部連携カタログ（と、この要求に基づいて書く文書）には、資格情報（API キー、トークン、パスワード、証明書）の値、個人を識別できる実データ、社外秘の連携先の内部情報を書かない。保管場所の区分、管理の手順、データの分類名など「所在と管理方法」だけを書く。
- 決定状態: 承認済み（Q-028 2026-10-16）　出自: AI提案　優先度: MUST（カタログは commit されて広く読まれ、一度記録された秘密は取り消せないため）
- 上位: G-004　出典: 既定制約 C-02、 C-02、NFR-SEC-005、SRC-022
- 対象エンティティ: 外部連携カタログ　関係する状態: なし　参照パラメータ: なし
- 関連する既存資産: NFR-SEC-005（API キーの保管・ログ）
- 受入基準 AC-430: 資格情報とみなす典型的な形式（`Bearer` の後の値、`api_key=`・`token=`・`password=` の後の値、32 文字以上の連続した英数字、`-----BEGIN` で始まる鍵・証明書の本文）の記述を含むカタログに対し、検査は失敗する。ただし、git の commit ハッシュ（40 桁の 16 進）と SHA のハッシュ値は誤検出として除外する。行に「例」と書いてあっても検出の対象外にはせず、検出した値が固定のダミー表記（`<ここに値>`、`xxxx`、`REDACTED`、アスタリスクだけの並び）である場合に限り失敗にしない（本物の値の素通りを防ぐため。Q-028 A の誤検出の扱いを具体化）。「API キー」などの語だけの説明文は、値を伴わないため失敗にしない。この機械検査は資格情報の形式の検出だけで、個人の実データと社外秘の内部情報は検査の対象外とし、レビューで確認する。
